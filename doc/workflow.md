# Workflow разработки (KISS)

Документ задает правила для кодового ассистента при разработке по `doc/vision.md` и `doc/tasklist.md`.

## 1) Базовые правила

- Работать строго по итерациям из `doc/tasklist.md` по порядку.
- Не перескакивать через итерации и не добавлять лишний функционал.
- Следовать принципу KISS: только необходимое для текущей итерации.

## 2) Цикл одной итерации

### Шаг 1. Подготовка и согласование
- Перед началом итерации предложить решение кратко:
  - какие файлы будут изменены;
  - какие блоки логики будут добавлены;
  - короткие отрезки (сниппеты) предполагаемого кода.
- Дождаться явного согласования от пользователя.

### Шаг 2. Реализация
- После согласования реализовать только задачи текущей итерации.
- Не трогать задачи следующих итераций.

### Шаг 3. Проверка
- Выполнить тест итерации из `doc/tasklist.md`.
- Кратко показать результат проверки (что работает / что не прошло).
- Дождаться подтверждения пользователя.

### Шаг 4. Фиксация прогресса
- Обновить `doc/tasklist.md`:
  - отметить выполненные чекбоксы текущей итерации;
  - обновить строку итерации в таблице прогресса (статус, % и краткий итог).
- Согласовать переход к следующей итерации.

### Шаг 5. Коммит
- После подтверждения пользователя сделать коммит в репозиторий:
  - один коммит на одну завершенную итерацию;
  - короткое и понятное сообщение (например: `Iter 1: scaffold and GUI start/stop buttons`).

## 3) Ограничения

- Не менять `doc/vision.md` без отдельного согласования.
- Если в итерации найден блокер, остановиться, кратко описать проблему и предложить 1-2 простых варианта решения.
