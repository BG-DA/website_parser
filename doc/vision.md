# Техническое видение проекта

Документ описывает техническое видение проекта парсера промокодов на основе требований из `doc/idea.md`.

## 1. Технологии (KISS для MVP)

- Язык: `Python 3.12`.
- GUI: `PySide6` (Qt for Python) для нативного desktop-интерфейса.
- HTTP-клиент: `httpx` (базовые таймауты и простые ретраи, без усложнений).
- Парсинг HTML: `BeautifulSoup4` + `lxml`.
- Валидация и модель данных: `pydantic`.
- Экспорт в Excel: `openpyxl` (формирование `.xlsx`).
- Логирование: стандартный `logging` + `RotatingFileHandler`.
- Упаковка в exe: `PyInstaller`.
- Тесты: `pytest` (минимальный набор smoke-тестов в MVP).

## 2. Принцип разработки (KISS)

- Подход: поэтапный `MVP -> доработка`.
- Стартуем с одного вертикального сценария: от ввода в GUI до сохранения `.xlsx`.
- На MVP используем простое модульное деление без избыточной слоистой архитектуры.
- Базовое правило: новая сложность добавляется только если без нее уже нельзя.
- Поисковые системы в MVP: 3 встроенных адаптера (`yandex`, `google`, `rambler`) без плагинного механизма.
- Тесты в MVP: минимальный набор `pytest` для ключевого happy-path и экспорта.

## 4. Архитектура проекта (KISS)

### 4.1 Основные компоненты

- `GUI`: ввод параметров и запуск процесса.
- `parser_flow`: единый orchestration-пайплайн.
- `adapters`: получение ссылок из `google`, `yandex`, `rambler`.
- `promocode_extractor`: извлечение промокодов из страниц.
- `xlsx_export`: сохранение результата.
- `rate_limiter` и `logger`: техническая поддержка процесса.

### 4.2 Поток выполнения

Единый pipeline без дополнительных архитектурных слоев:

1. `GUI -> parser_flow`.
2. `parser_flow -> adapters` (по выбранным пользователем системам).
3. Сбор URL из выдачи и загрузка страниц.
4. Извлечение и нормализация промокодов.
5. Дедупликация в памяти (`set`).
6. Экспорт в `.xlsx`.
7. Возврат статуса и статистики в GUI.

### 4.3 Многопоточная обработка

- Используется `ThreadPoolExecutor` для I/O-задач.
- Количество потоков поиска: по числу выбранных пользователем поисковых систем (`1..3`).
- Каждый адаптер выполняется в отдельном worker-потоке.
- Дедупликация и итоговый список собираются в общем потоке с потокобезопасным объединением результатов.
- GUI обновляется только из главного потока через сигналы.

### 4.4 Внутренний таймер запросов (anti-blocking)

- Для каждого домена и каждого поискового движка применяется внутренний rate limiter.
- Запросы отправляются не "вплотную", а с настраиваемой паузой и небольшим случайным jitter.
- При ошибках `429/403/5xx` включается экспоненциальный backoff.
- Поддерживается глобальный лимит RPS и локальные лимиты по источникам.
- Таймер управляет интервалами между попытками и ограничивает burst-нагрузку.
- В лог записываются события задержек, backoff и превышений лимитов для диагностики.

### 4.5 Точка расширения под историю запусков

- В MVP история запусков не сохраняется.
- Архитектурно предусматривается подключение отдельного модуля `history_store` без изменения основного pipeline.
- Интерфейс расширения: сохранить `run_id`, время запуска, параметры и итоговую статистику.

## 5. Модель данных (KISS)

### 5.1 Сущности

- `SearchRequest` (входные параметры запуска)
  - `search_engines: list[str]`
  - `queries: list[str]`
  - `depth_pages: int`
  - `output_path: str`

- `PromocodeRecord` (итоговая запись для экспорта)
  - `promocode: str`
  - `source_url: str`
  - `search_engine: str`
  - `search_query: str`
  - `detected_at: datetime`

- `RunStats` (итоги выполнения)
  - `total_queries: int`
  - `total_urls_checked: int`
  - `total_promocodes_found: int`
  - `duration_sec: float`
  - `errors_count: int`

### 5.2 Формат XLSX

Листы:
- `Promocodes` (основной лист):
  - `Promocode`
  - `Source URL`
  - `Search Engine`
  - `Search Query`
  - `Detected At`
- `Summary`:
  - `total_queries`;
  - `total_urls_checked`;
  - `total_promocodes_found`;
  - `duration_sec`;
  - `errors_count`.

## 6. Сценарии работы (KISS)

### 6.1 Основной сценарий (MVP)

1. Пользователь запускает `.exe`.
2. Выбирает поисковые системы (`google`, `yandex`, `rambler`).
3. Вводит ключевые фразы и глубину поиска.
4. Выбирает путь сохранения `.xlsx`.
5. Нажимает `Старт`.
6. Видит прогресс и может нажать `Стоп` для мягкой остановки текущего запуска.
7. По завершении получает `.xlsx` и краткую статистику (`RunStats`) в GUI.

### 6.2 Нештатные сценарии

- Ошибка сети / ограничение доступа (`429/403`): показать понятное сообщение, применить backoff, записать детали в лог.
- Пустая выдача: создать `.xlsx` с пустым листом `Promocodes` и заполненным `Summary`.
- Ошибка пути сохранения: показать ошибку и запросить корректный путь.

## 7. Деплой (KISS)

### 7.1 Сборка

- Целевая платформа MVP: только Windows.
- Сборка `.exe` через `PyInstaller` в режиме `onefile`.
- `onedir` в MVP не используется.

### 7.2 Артефакты

- Выходной артефакт: `dist/promocode_parser.exe`.
- Доставка пользователю: один `.exe` файл.
- Инсталлятор (`.msi` / `setup.exe`) в MVP не используется.

### 7.3 Процесс выпуска

- Сборка выполняется локально.
- После сборки выполняется ручная smoke-проверка запуска и базового сценария.
- CI/CD сборка в MVP не внедряется.

## 8. Подход к конфигурированию (KISS)

- Формат конфига: `YAML` (`config/config.yaml`).
- Если файл отсутствует, приложение использует значения по умолчанию из кода.
- Приоритет источников:
  1. значения, заданные пользователем в GUI;
  2. значения из `config/config.yaml`;
  3. встроенные значения по умолчанию.
- Редактирование конфига поддерживается в GUI (базовая форма настроек).
- Минимальный набор параметров:
  - `network.timeout_seconds`;
  - `network.max_retries`;
  - `network.min_request_delay_ms`;
  - `network.max_request_delay_ms`;
  - `network.jitter_ms`;
  - `network.backoff_base_ms`;
  - `parser.search_workers_per_engine`;
  - `logging.level`;
  - `logging.path`.
- Настройки валидируются при запуске и перед стартом парсинга.

## 9. Подход к логгированию (KISS)

- Логирование в файл (основной режим MVP).
- Уровни:
  - `INFO`: ключевые этапы выполнения;
  - `WARNING`: частичные ошибки;
  - `ERROR`: ошибки, мешающие шагу сценария;
  - `DEBUG`: дополнительная диагностика при включении debug-режима.
- Обязательное поле `run_id` в каждой записи лога для привязки событий к запуску.
- Формат записи: `timestamp`, `level`, `module`, `run_id`, `message`.
- Ротация логов: 1 активный файл + 2 backup-файла.
- В MVP промокоды в логах не маскируются (логируются как есть).
- Минимально логируемые события: старт, стоп, ошибки запросов, экспорт, итоговая статистика.

## 10. Границы MVP и расширения (KISS)

### 10.1 Что входит в MVP (обязательно)

- Desktop GUI на `PySide6` с параметрами запуска парсинга.
- 3 встроенных адаптера: `google`, `yandex`, `rambler`.
- Многопоточность по выбранным поисковым системам (`1..3` потока).
- Внутренний таймер запросов: задержки, jitter, базовый backoff.
- Извлечение промокодов и экспорт в `.xlsx` (`Promocodes` + `Summary`).
- Управление запуском через `Старт` / `Стоп` (мягкая остановка).
- Конфиг через `config/config.yaml` + редактирование базовых настроек в GUI.
- Базовое логирование в файл с `run_id`.
- Минимальные `pytest` smoke-тесты ключевого сценария.

### 10.2 Что не входит в MVP (после проверки идеи)

- Модуль сохранения истории запусков (архитектурная точка расширения уже предусмотрена).
- CI/CD сборка и автоматические релизные пайплайны.
- Инсталлятор (`.msi` / `setup.exe`).
- Дополнительные форматы выгрузки (`csv`, `json`).
- Расширенные anti-bot механики (прокси, антикапча и т.п.).
